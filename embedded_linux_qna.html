Q1Kernel space khác user space thế nào? System call đi từ ứng dụng xuống kernel ra sao?Kernel space vs user space. How does a system call travel from an app to the kernel?

Hãy hình dung một nhà hàng. Khách (ứng dụng) ngồi ở phòng ăn, không được vào bếp. Bếp (kernel) có dao, lửa, nguyên liệu, tức là phần cứng. Khách muốn món gì thì gọi phục vụ (system call).

User spaceKernel space
Ai chạy ở đâyỨng dụng, thư viện (libc), shellKernel, driver, scheduler, quản lý bộ nhớ
Quyền CPUThấp (ARM64: EL0, x86: ring 3)Cao (ARM64: EL1, x86: ring 0)
Truy cập phần cứngKhông trực tiếpTrực tiếp
Khi bị lỗiChỉ process đó chết (segfault)Cả hệ thống có thể treo (kernel panic)

Đường đi của một system call, ví dụ write():

  1. Ứng dụng gọi write(fd, buf, len). Đây là hàm bọc (wrapper) trong libc.
  2. libc đặt số hiệu syscall vào thanh ghi (ARM64: x8, x86-64: rax) và các tham số vào những thanh ghi khác.
  3. libc chạy một lệnh đặc biệt (ARM64: svc #0, x86-64: syscall). CPU chuyển sang chế độ kernel và nhảy tới điểm vào đã định sẵn.
  4. Kernel tra bảng syscall theo số hiệu, gọi sys_write().
  5. sys_write đi qua VFS, tới driver của file hoặc thiết bị đó, driver ghi xuống phần cứng.
  6. Kết quả trả về qua thanh ghi, CPU quay lại user mode, ứng dụng chạy tiếp.

Picture a restaurant. The customer (application) sits in the dining room and may not enter the kitchen. The kitchen (kernel) holds the knives, fire and ingredients, which is the hardware. The customer orders through a waiter (system call).

User spaceKernel space
What runs hereApps, libraries (libc), shellKernel, drivers, scheduler, memory manager
CPU privilegeLow (ARM64: EL0, x86: ring 3)High (ARM64: EL1, x86: ring 0)
Hardware accessNot directDirect
On a bugOnly that process dies (segfault)The whole system can stop (kernel panic)

The path of one system call, for example write():

  1. The app calls write(fd, buf, len). This is a wrapper function in libc.
  2. libc puts the syscall number in a register (ARM64: x8, x86-64: rax) and the arguments in other registers.
  3. libc runs a special instruction (ARM64: svc #0, x86-64: syscall). The CPU switches to kernel mode and jumps to a fixed entry point.
  4. The kernel looks the number up in the syscall table and calls sys_write().
  5. sys_write goes through the VFS to the driver for that file or device, and the driver writes to hardware.
  6. The result comes back in a register, the CPU returns to user mode, and the app continues.
app→libc write()→svc / syscall→syscall table→VFS→driver→hardware

Q2Các bước cross-compile kernel? Bật/tắt config nào cho automotive và vì sao?Steps to cross-compile the kernel? Which configs for automotive, and why?

Cross-compile nghĩa là build trên PC (x86) nhưng tạo ra file chạy cho board (ARM). Lý do: board yếu, build kernel trên board mất nhiều giờ.

  1. Cài toolchain cho kiến trúc đích (ví dụ aarch64-linux-gnu-gcc).
  2. Lấy source kernel (thường từ nhà sản xuất chip, vì có sẵn driver cho board).
  3. Đặt 2 biến: ARCH (kiến trúc) và CROSS_COMPILE (tiền tố của toolchain).
  4. Nạp cấu hình mặc định của board: make <board>_defconfig.
  5. Chỉnh cấu hình: make menuconfig.
  6. Build kernel image, device tree (DTB) và module.
  7. Chép Image, file .dtb và thư mục module sang board.

Cross-compiling means building on a PC (x86) but producing files that run on the board (ARM). The reason: the board is slow, and building a kernel on it takes hours.

  1. Install a toolchain for the target architecture (for example aarch64-linux-gnu-gcc).
  2. Get the kernel source (usually from the chip vendor, because it already has the board drivers).
  3. Set two variables: ARCH (architecture) and CROSS_COMPILE (toolchain prefix).
  4. Load the board's default config: make <board>_defconfig.
  5. Adjust the config: make menuconfig.
  6. Build the kernel image, device tree (DTB) and modules.
  7. Copy Image, the .dtb file and the modules directory to the board.

Ví dụExample

export ARCH=arm64
export CROSS_COMPILE=aarch64-linux-gnu-

make defconfig                 # or: make <your_board>_defconfig
make menuconfig                # turn options on/off
make -j$(nproc) Image dtbs modules
make modules_install INSTALL_MOD_PATH=/path/to/rootfs

# results
arch/arm64/boot/Image
arch/arm64/boot/dts/<vendor>/<board>.dtb

Q3Kernel build xong nhưng không chạy trên board. Kiểm tra gì trước?The kernel built but does not run on the board. What do you check first?

Kiểm tra theo thứ tự từ dễ đến khó:

  1. Đúng kiến trúc chưa? file vmlinux phải báo ARM aarch64, không phải x86-64. Quên ARCH là lỗi rất hay gặp.
  2. Đúng loại image chưa? ARM64 dùng Image với lệnh booti; ARM 32-bit dùng zImage với bootz; uImage dùng bootm.
  3. DTB có đúng board không? DTB sai thì kernel không biết UART, RAM nằm ở đâu và sẽ im lặng.
  4. bootargs: console= có đúng cổng và baudrate không? root= có trỏ đúng phân vùng không?
  5. Địa chỉ load: kernel và DTB có đè lên nhau trong RAM không?
  6. Driver thiết yếu (UART, eMMC/SD, filesystem ext4) có build dạng built-in không?
  7. File có hỏng khi chép không? So sánh kích thước hoặc md5sum.

Check from easiest to hardest:

  1. Right architecture? file vmlinux must say ARM aarch64, not x86-64. Forgetting ARCH is a very common mistake.
  2. Right image type? ARM64 uses Image with booti; 32-bit ARM uses zImage with bootz; uImage uses bootm.
  3. Does the DTB match the board? With the wrong DTB the kernel does not know where the UART and RAM are, and stays silent.
  4. bootargs: is console= the right port and baud rate? Does root= point at the right partition?
  5. Load addresses: do the kernel and DTB overlap in RAM?
  6. Essential drivers (UART, eMMC/SD, ext4) built in rather than as modules?
  7. Was the file damaged while copying? Compare size or md5sum.

Ví dụExample

$ file vmlinux
vmlinux: ELF 64-bit LSB executable, ARM aarch64, ...   # good

$ grep -E "CONFIG_SERIAL_.*CONSOLE|CONFIG_MMC=|CONFIG_EXT4_FS=" .config
CONFIG_SERIAL_8250_CONSOLE=y
CONFIG_MMC=y
CONFIG_EXT4_FS=y                                       # =y, not =m

Q4Chuỗi boot: bootloader → kernel → init → userspace. Mỗi bước làm gì?The boot chain: bootloader → kernel → init → userspace. What does each step do?

BướcStageNhiệm vụJob
ROM codeCode cứng trong chip. Chạy đầu tiên khi cấp nguồn, tìm thiết bị boot (SD, eMMC) và nạp SPL.Code burned into the chip. Runs first at power-on, finds the boot device (SD, eMMC) and loads the SPL.
SPLBootloader nhỏ. Khởi tạo RAM (DDR) rồi nạp U-Boot đầy đủ vào RAM.A tiny bootloader. Initialises RAM (DDR), then loads full U-Boot into RAM.
U-BootKhởi tạo UART, storage, mạng. Nạp kernel + DTB vào RAM, truyền bootargs, rồi nhảy vào kernel.Sets up UART, storage, network. Loads kernel + DTB into RAM, passes bootargs, then jumps to the kernel.

Q5Board dừng ở "Starting kernel..." và im lặng. Phân tích và debug thế nào?The board stops at "Starting kernel..." with no more log. How do you analyse and debug?

Dòng này là dòng cuối cùng của U-Boot. Sau nó là việc của kernel. Im lặng có hai khả năng: kernel đang chạy nhưng không in ra được, hoặc kernel chết ngay từ đầu.

Nguyên nhânCách kiểm tra
Sai console= trong bootargs (hay gặp nhất)printenv bootargs. Tên cổng phải khớp driver, ví dụ ttyS0, ttyAMA0, ttymxc0.
Sai hoặc thiếu DTBKiểm tra tên file .dtb; dùng fdt addr, fdt print /model trong U-Boot.
Địa chỉ load chồng lên nhauSo sánh kernel_addr_r, fdt_addr_r với kích thước image.
Sai kiến trúc / sai loại imagefile vmlinux trên PC; dùng đúng booti/bootz.
Kernel thiếu driver serial consoleXem .config.

Công cụ mạnh nhất là earlycon: cho kernel in log rất sớm, trước khi driver console chính thức chạy. Nếu có log với earlycon thì kernel vẫn sống, lỗi nằm ở cấu hình console. Nếu vẫn im lặng thì nghi DTB, địa chỉ load hoặc image.

That line is the last line from U-Boot. Everything after it is the kernel's job. Silence has two possible meanings: the kernel is running but cannot print, or it died right at the start.

CauseHow to check
Wrong console= in bootargs (most common)printenv bootargs. The port name must match the driver, e.g. ttyS0, ttyAMA0, ttymxc0.
Wrong or missing DTBCheck the .dtb file name; use fdt addr, fdt print /model in U-Boot.
Overlapping load addressesCompare kernel_addr_r, fdt_addr_r with the image size.
Wrong architecture / image typefile vmlinux on the PC; use the right booti/bootz.
Kernel lacks the serial console driverLook in .config.

The strongest tool is earlycon: it makes the kernel print very early, before the real console driver starts. If logs appear with earlycon, the kernel is alive and the fault is in the console setup. If it is still silent, suspect the DTB, load addresses or the image.

Ví dụExample

=> printenv bootargs
bootargs=console=ttyS1,115200 root=/dev/mmcblk0p2 rootwait   # board uses ttyS0 → silent

=> setenv bootargs console=ttyS0,115200 earlycon root=/dev/mmcblk0p2 rootwait
=> boot
[    0.000000] earlycon: uart8250 at MMIO 0x... (options '')  # now we see logs

Q6Dùng serial console và U-Boot để xác định lỗi boot thế nào?How do you use the serial console and U-Boot to locate a boot failure?

Serial console là kênh debug đầu tiên vì nó hoạt động trước cả màn hình và mạng. Nối USB-UART (TX, RX, GND), mở terminal ở 115200 8N1. Ý tưởng chính: log dừng ở đâu thì lỗi ở giai đoạn đó.

Triệu chứngGiai đoạn lỗiNghi ngờ
Không có ký tự nàoROM / SPLNguồn, dây TX/RX ngược, baudrate, thẻ SD ghi sai
Có SPL, không có U-BootSPLKhởi tạo DDR, file U-Boot hỏng
U-Boot báo không đọc được fileU-BootSai phân vùng, sai tên file

VFS: Unable to mount root fsKernel muộnSai root=, thiếu driver storage/filesystem, thiếu rootwait
No working init foundinitRootfs thiếu /sbin/init hoặc sai kiến trúc

Nhấn một phím để dừng autoboot, sau đó boot thủ công từng bước để thấy bước nào hỏng.

The serial console is the first debug channel because it works before the display and network do. Connect a USB-UART adapter (TX, RX, GND) and open a terminal at 115200 8N1. The main idea: where the log stops is the stage that failed.

SymptomFailing stageSuspect
No characters at allROM / SPLPower, swapped TX/RX, baud rate, badly written SD card

Press a key to stop autoboot, then boot by hand, one step at a time, to see which step breaks.

Ví dụ: boot thủ công trong U-BootExample: manual boot in U-Boot

$ sudo minicom -D /dev/ttyUSB0 -b 115200     # on the PC

=> mmc list ; mmc dev 0                      # is the SD/eMMC detected?

=> booti ${kernel_addr_r} - ${fdt_addr_r}    # "-" means no initramfs
=> saveenv                                   # only after it works

Q7Phân biệt layer, recipe, BitBake. Image được build ra thế nào?Layer, recipe and BitBake. How is an image built from them?

Là gìWhat it isSo sánh với nấu ănCooking analogy
Recipe (.bb)File mô tả cách build một phần mềm: lấy source ở đâu, compile thế nào, cài vào đâu.A file describing how to build one piece of software: where the source is, how to compile, where to install.Công thức một mónThe recipe for one dish
Layer (meta-*)Thư mục gom các recipe và cấu hình cùng chủ đề (BSP, Qt, ứng dụng của công ty).A directory grouping related recipes and config (BSP, Qt, your company's apps).Cuốn sách nấu ănA cookbook
BitBakeCông cụ đọc recipe, tính thứ tự phụ thuộc và chạy các task.The tool that reads recipes, works out dependencies and runs the tasks.Đầu bếpThe chef
ImageCũng là một recipe, liệt kê các package vào rootfs.Also a recipe; it lists the packages that go in the rootfs.Thực đơn bữa tiệcThe banquet menu

Khi chạy bitbake core-image-minimal:

  1. Đọc conf/bblayers.conf (dùng layer nào) và conf/local.conf (MACHINE nào).
  2. Parse tất cả recipe, dựng cây phụ thuộc.
  3. Với mỗi recipe, chạy lần lượt các task bên dưới.
  4. Gom package thành rootfs (do_rootfs), tạo file image (do_image).
  5. Kết quả nằm ở tmp/deploy/images/<machine>/.

When you run bitbake core-image-minimal:

  1. It reads conf/bblayers.conf (which layers) and conf/local.conf (which MACHINE).
  2. It parses every recipe and builds the dependency tree.
  3. For each recipe it runs the tasks below in order.
  4. It assembles packages into a rootfs (do_rootfs) and creates the image file (do_image).
  5. Output lands in tmp/deploy/images/<machine>/.
do_fetch→do_unpack→do_patch→do_configure→do_compile→do_install→do_package→do_rootfs→do_image

Ví dụExample

$ source oe-init-build-env build      # enter the build directory
$ bitbake-layers show-layers          # which layers are active
$ bitbake-layers show-recipes "busy*" # which layer provides busybox
$ bitbake core-image-minimal          # build the image
$ bitbake -c listtasks busybox        # all tasks of one recipe

Q8Viết recipe cơ bản có SRC_URI, do_compile, do_install. Đưa package vào image thế nào?Write a basic recipe with SRC_URI, do_compile, do_install. How do you add the package to an image?

Cấu trúc layer của bạn:Your layer layout:

meta-mylayer/
├── conf/layer.conf
└── recipes-example/hello/
    ├── hello_1.0.bb
    └── files/hello.c

hello_1.0.bb

SUMMARY = "Simple hello world program"
LICENSE = "MIT"
LIC_FILES_CHKSUM = "file://${COMMON_LICENSE_DIR}/MIT;md5=0835ade698e0bcf8506ecda2f7b4f302"

SRC_URI = "file://hello.c"          # where the source comes from
S = "${WORKDIR}"                    # where the source sits after unpack

do_compile() {
    ${CC} ${CFLAGS} ${LDFLAGS} hello.c -o hello     # ${CC} is the cross compiler
}

do_install() {
    install -d ${D}${bindir}                 # create /usr/bin inside the package
    install -m 0755 hello ${D}${bindir}/     # copy the binary there
}
  • SRC_URI: nguồn. file:// là file cạnh recipe; cũng có thể là git:// hay https://.
  • do_compile: luôn dùng ${CC}, không gõ gcc, vì gcc là compiler của PC.
  • do_install: ${D} là thư mục tạm đóng vai trò gốc / của board. ${bindir} là /usr/bin.

Đưa vào image: thêm một dòng vào conf/local.conf (hoặc vào recipe image của bạn), rồi build lại.

  • SRC_URI: the source. file:// is a file next to the recipe; it can also be git:// or https://.
  • do_compile: always use ${CC}, never plain gcc, because gcc is the PC's compiler.
  • do_install: ${D} is a temporary directory that plays the role of the board's /. ${bindir} is /usr/bin.

To add it to an image: put one line in conf/local.conf (or in your image recipe), then rebuild.

IMAGE_INSTALL:append = " hello"      # the leading space is required

$ bitbake-layers add-layer ../meta-mylayer
$ bitbake hello                      # test the recipe alone first
$ bitbake core-image-minimal
Lưu ý phiên bản:Version notes: bản Yocto cũ (trước Honister 3.4) viết IMAGE_INSTALL_append. Các bản rất mới unpack source vào ${UNPACKDIR} nên dùng S = "${UNPACKDIR}". Hãy xem recipe có sẵn trong bản Yocto của bạn để theo đúng kiểu.old Yocto releases (before Honister 3.4) write IMAGE_INSTALL_append. Very recent releases unpack sources into ${UNPACKDIR}, so use S = "${UNPACKDIR}". Look at an existing recipe in your release and follow its style.

Q9Tích hợp BSP layer cho board mới trong Yocto thế nào? Chỉnh file nào?How do you integrate a BSP layer for a new board in Yocto? Which files change?

BSP layer (Board Support Package) chứa mọi thứ riêng của phần cứng: cấu hình machine, recipe kernel, U-Boot, device tree, firmware.

  1. Lấy BSP layer của hãng (ví dụ meta-raspberrypi, meta-ti, meta-freescale), chọn đúng branch trùng với bản Yocto (kirkstone, scarthgap...).
  2. Thêm layer vào conf/bblayers.conf, kèm các layer mà nó phụ thuộc.
  3. Đặt MACHINE trong conf/local.conf.
  4. Nếu là board tự thiết kế: tạo conf/machine/myboard.conf trong layer của bạn, dựa trên machine gần giống nhất.
  5. Tuỳ biến kernel bằng file .bbappend: thêm device tree, defconfig, patch.
  6. Build, nạp lên board, kiểm tra qua serial console.

A BSP layer (Board Support Package) holds everything specific to the hardware: machine config, kernel recipe, U-Boot, device tree, firmware.

  1. Get the vendor BSP layer (for example meta-raspberrypi, meta-ti, meta-freescale) on the branch matching your Yocto release (kirkstone, scarthgap...).
  2. Add the layer to conf/bblayers.conf, along with the layers it depends on.
  3. Set MACHINE in conf/local.conf.
  4. For a custom board: create conf/machine/myboard.conf in your own layer, based on the closest existing machine.
  5. Customise the kernel with a .bbappend: add a device tree, defconfig, patches.
  6. Build, flash, and check over the serial console.

Q12Viết một kernel module điều khiển GPIO. init/exit và đăng ký thiết bị hoạt động ra sao?Write a kernel module that drives a GPIO. How do init/exit and device registration work?

Module dưới đây tạo file /dev/myled. Ghi 1 thì LED sáng, ghi 0 thì tắt.

  • init chạy khi insmod: xin tài nguyên (GPIO) và đăng ký thiết bị với kernel. Sau bước đăng ký, kernel tạo /dev/myled và biết gọi hàm nào khi ứng dụng write.
  • exit chạy khi rmmod: làm ngược lại theo thứ tự ngược. Quên trả tài nguyên là lỗi phổ biến.
  • file_operations là bảng nối system call của ứng dụng với hàm trong driver.
  • copy_from_user là bắt buộc: kernel không được đọc thẳng con trỏ từ user space.

The module below creates /dev/myled. Writing 1 turns the LED on, 0 turns it off.

  • init runs on insmod: it claims resources (the GPIO) and registers the device with the kernel. After registration the kernel creates /dev/myled and knows which function to call when an app does write.
  • exit runs on rmmod: it undoes everything in reverse order. Forgetting to release resources is a common bug.
  • file_operations is the table linking an app's system calls to driver functions.
  • copy_from_user is mandatory: the kernel must not read a user-space pointer directly.

myled.c

#include <linux/module.h>
#include <linux/fs.h>
#include <linux/miscdevice.h>
#include <linux/uaccess.h>
#include <linux/gpio.h>

#define LED_GPIO 17                 /* change to your board's GPIO number */

/* called when user space does write() on /dev/myled */
static ssize_t led_write(struct file *f, const char __user *buf,
                         size_t len, loff_t *off)
{
    char c;

    if (len < 1)
        return 0;
    if (copy_from_user(&c, buf, 1))     /* safely copy 1 byte from the app */
        return -EFAULT;

    if (c == '1')
        gpio_set_value(LED_GPIO, 1);
    else if (c == '0')
        gpio_set_value(LED_GPIO, 0);
    return len;                          /* tell the app all bytes were used */
}

static const struct file_operations led_fops = {
    .owner = THIS_MODULE,
    .write = led_write,
};

static struct miscdevice led_dev = {
    .minor = MISC_DYNAMIC_MINOR,         /* kernel picks a free minor number */
    .name  = "myled",                    /* becomes /dev/myled */
    .fops  = &led_fops,
};

static int __init led_init(void)
{
    int ret;

    ret = gpio_request(LED_GPIO, "myled");      /* 1. claim the pin */
    if (ret)
        return ret;
    gpio_direction_output(LED_GPIO, 0);         /* 2. output, start low */

    ret = misc_register(&led_dev);              /* 3. register → /dev/myled */
    if (ret) {
        gpio_free(LED_GPIO);                    /* undo step 1 on failure */
        return ret;
    }
    pr_info("myled: loaded\n");
    return 0;
}

static void __exit led_exit(void)
{
    misc_deregister(&led_dev);                  /* reverse order of init */
    gpio_set_value(LED_GPIO, 0);
    gpio_free(LED_GPIO);
    pr_info("myled: unloaded\n");
}

module_init(led_init);
module_exit(led_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Simple GPIO LED driver");

Q14Cấu trúc CAN frame, cơ chế arbitration và error handlingCAN frame structure, arbitration and error handling

CAN là bus mà mọi ECU cùng nối vào hai dây CAN_H và CAN_L. Không có địa chỉ người nhận: mỗi frame mang một ID nói lên nội dung (ví dụ 0x0C4 = tốc độ động cơ), ECU nào quan tâm thì nhận.CAN is a bus where every ECU shares two wires, CAN_H and CAN_L. There is no destination address: each frame carries an ID that names its content (for example 0x0C4 = engine speed), and any ECU that cares picks it up.

Arbitration. Bus có hai mức: dominant (0) và recessive (1). Nếu một node gửi 0 và node khác gửi 1 cùng lúc, bus sẽ là 0. Mỗi node vừa gửi vừa đọc lại bus. Node nào gửi 1 mà đọc thấy 0 thì biết mình thua, lập tức dừng và chờ lượt sau. Hệ quả: ID nhỏ hơn có ưu tiên cao hơn, và frame thắng không bị hỏng, không mất thời gian.

Error handling. Có 5 loại lỗi: bit error, stuff error (quá 5 bit giống nhau liên tiếp), CRC error, form error, ACK error. Node phát hiện lỗi sẽ gửi error frame để huỷ frame đó, node gửi tự gửi lại. Mỗi node có hai bộ đếm: TEC (lỗi khi gửi) và REC (lỗi khi nhận).

Arbitration. The bus has two levels: dominant (0) and recessive (1). If one node sends 0 while another sends 1, the bus reads 0. Every node reads the bus back while sending. A node that sends 1 but reads 0 knows it lost, stops at once and waits for the next slot. The result: the lower ID has higher priority, and the winning frame is not damaged and loses no time.

Error handling. There are 5 error types: bit error, stuff error (more than 5 equal bits in a row), CRC error, form error, ACK error. A node that detects one sends an error frame to cancel that frame, and the sender retransmits automatically. Each node keeps two counters: TEC (transmit errors) and REC (receive errors).

Q16Hai ECU gửi cùng lúc, hoặc bus báo lỗi nhiều. Phân tích và xử lý ra sao?Two ECUs transmit together, or the bus reports many errors. How do you analyse and fix it?

Hai ECU gửi cùng lúc là chuyện bình thường, không phải lỗi. Arbitration (Q14) giải quyết: ID nhỏ thắng, bên thua tự gửi lại ngay sau đó. Chỉ có vấn đề trong hai trường hợp:

  • Hai ECU dùng cùng một ID nhưng dữ liệu khác nhau. Arbitration hoà, đến phần data thì xung đột và sinh bit error. Cách sửa: mỗi ID chỉ thuộc về một ECU (kiểm tra file DBC).
  • Frame ID lớn bị chờ mãi vì bus quá tải. Đo bằng canbusload, giảm tần suất gửi hoặc đổi ID quan trọng thành nhỏ hơn.

Bus báo lỗi nhiều. Kiểm tra từ lớp vật lý trở lên:

  1. Bitrate của mọi node có giống nhau không? Đây là nguyên nhân số một.
  2. Điện trở đầu cuối: phải có 120 Ω ở hai đầu bus. Tắt nguồn, đo giữa CAN_H và CAN_L phải ra khoảng 60 Ω.
  3. Dây: CAN_H/CAN_L có bị đảo, đứt, chạm mass không? Các node có chung GND không?
  4. Bộ đếm lỗi và trạng thái: dùng lệnh bên dưới để xem node đang Error Active, Passive hay Bus Off.
  5. Xem error frame để biết loại lỗi (ACK, bit, stuff...).
  6. Rút từng ECU ra để tìm node gây nhiễu. Dùng oscilloscope xem dạng sóng nếu cần.

Two ECUs transmitting at once is normal, not a fault. Arbitration (Q14) settles it: the lower ID wins and the loser retries right after. It is a problem only in two cases:

  • Two ECUs use the same ID with different data. Arbitration ties, then the data fields collide and cause bit errors. Fix: each ID belongs to exactly one ECU (check the DBC file).
  • A high-ID frame waits forever because the bus is overloaded. Measure with canbusload, lower the send rate, or give important messages lower IDs.

Many bus errors. Check from the physical layer up:

  1. Is the bitrate the same on every node? This is the number one cause.
  2. Termination: there must be 120 Ω at both ends of the bus. With power off, measuring between CAN_H and CAN_L should give about 60 Ω.
  3. Wiring: are CAN_H/CAN_L swapped, broken or shorted? Do the nodes share ground?
  4. Error counters and state: use the commands below to see whether the node is Error Active, Passive or Bus Off.
  5. Watch the error frames to learn the error type (ACK, bit, stuff...).
  6. Unplug ECUs one at a time to find the one disturbing the bus. Use an oscilloscope on the waveform if needed.

Ví dụExample

    can state ERROR-PASSIVE (berr-counter tx 128 rx 0) restart-ms 0
    bitrate 500000 sample-point 0.875

    0          153        0          1          1          0

Auto-restart only hides the symptom; you still need the root cause.

Q17Kiểm tra camera /dev/video* và định dạng hỗ trợ. V4L2 hoạt động theo luồng nào?Checking a camera at /dev/video* and its formats. What is the V4L2 flow?

V4L2 (Video for Linux 2) là giao diện chuẩn của kernel cho camera. Mỗi camera hiện ra là một character device /dev/videoN, điều khiển bằng ioctl.V4L2 (Video for Linux 2) is the kernel's standard interface for cameras. Each camera appears as a character device /dev/videoN, controlled with ioctl.

Q18Viết GStreamer pipeline capture, xử lý và hiển thị video từ camera. Vai trò từng element?Write a GStreamer pipeline to capture, process and display camera video. What does each element do?

GStreamer giống một dây chuyền: mỗi element làm một việc, nối với nhau bằng dấu !. Dữ liệu chảy từ source qua các filter tới sink.GStreamer works like an assembly line: each element does one job, and elements are joined with !. Data flows from a source through filters to a sink.

Ví dụExample

gst-launch-1.0 v4l2src device=/dev/video0 \
  ! video/x-raw,width=640,height=480,framerate=30/1 \
  ! videoconvert \
  ! videoflip method=horizontal-flip \
  ! videoscale ! video/x-raw,width=1280,height=720 \
  ! autovideosink sync=false
ElementVai tròRole
v4l2srcSource. Đọc frame từ camera qua V4L2 (làm hết các bước ở Q17 giúp bạn).Source. Reads frames from the camera through V4L2 (it does all the Q17 steps for you).
video/x-raw,...Caps filter. Không xử lý gì, chỉ yêu cầu định dạng: kích thước, fps. Phải là định dạng camera hỗ trợ.Caps filter. It processes nothing; it only requests a format: size, fps. It must be one the camera supports.
videoconvertĐổi không gian màu (ví dụ YUYV sang định dạng màn hình cần).Converts colour space (for example YUYV to what the display needs).

#include <gst/gst.h>

int main(int argc, char *argv[])
{
    GstElement *pipeline;
    GstBus *bus;
    GstMessage *msg;

    gst_init(&argc, &argv);

    /* same text as the gst-launch command line */
    pipeline = gst_parse_launch(
        "v4l2src device=/dev/video0 ! videoconvert ! autovideosink sync=false",
        NULL);

    gst_element_set_state(pipeline, GST_STATE_PLAYING);

    /* block here until an error or end-of-stream */
    bus = gst_element_get_bus(pipeline);
    msg = gst_bus_timed_pop_filtered(bus, GST_CLOCK_TIME_NONE,
                                     GST_MESSAGE_ERROR | GST_MESSAGE_EOS);

    if (msg != NULL)
        gst_message_unref(msg);
    gst_object_unref(bus);
    gst_element_set_state(pipeline, GST_STATE_NULL);
    gst_object_unref(pipeline);
    return 0;
}

Q19Thiết kế camera lùi / camera 360 bằng V4L2 và GStreamer. Xử lý độ trễ và mất frame thế nào?Design a rear-view / 360° camera with V4L2 and GStreamer. How do you handle latency and dropped frames?

Kiến trúc tổng thểOverall architecture

Camera sensor→CSI / SerDes→V4L2 driver→GStreamer→GPU / compositor→Display
CAN: gear = R→camera service→hiện / ẩn videoshow / hide video
  • Camera lùi: một camera. Một service nghe CAN (SocketCAN); khi thấy tín hiệu số lùi thì đưa video lên trên cùng màn hình, kèm đường gióng (overlay). Ảnh phải lật ngang.
  • Camera 360: bốn camera mắt cá (trước, sau, trái, phải). Mỗi ảnh cần: hiệu chỉnh méo, chiếu thành góc nhìn từ trên xuống, rồi ghép lại quanh hình chiếc xe. Phần này nặng nên làm trên GPU (OpenGL), và bốn camera phải đồng bộ thời gian.
  • Khởi động sớm: camera lùi phải hiện rất nhanh sau khi vào số lùi (quy định Mỹ FMVSS 111 yêu cầu trong 2 giây). Vì vậy service camera khởi động từ rất sớm trong quá trình boot, không chờ toàn bộ giao diện.

Giảm độ trễ

  • Không nén, không giải nén: dùng định dạng raw (YUYV, NV12), tránh MJPEG/H.264 trên đường hiển thị.
  • Không copy: dùng DMABUF để camera, GPU và màn hình dùng chung một buffer.
  • Dùng phần cứng để đổi màu và scale thay cho videoconvert chạy trên CPU.
  • Sink đặt sync=false; hàng đợi nhỏ và leaky để bỏ frame cũ thay vì dồn lại. Với camera lùi, ảnh mới quan trọng hơn ảnh đủ.
  • Hiển thị trực tiếp qua kmssink hoặc waylandsink.
  • Đo "glass-to-glass": quay camera vào một đồng hồ mili-giây, chụp cả đồng hồ và màn hình, lấy hiệu.

Xử lý mất frame và lỗi

  • Phát hiện: mỗi buffer V4L2 có số thứ tự (sequence); số nhảy cóc là mất frame. Theo dõi thêm thông điệp QoS và ERROR trên GStreamer bus.
  • Nguyên nhân thường gặp: CPU quá tải, băng thông USB không đủ, ít buffer, dây hoặc đầu nối kém.
  • Phục hồi: dùng watchdog; nếu quá một khoảng thời gian không có frame mới thì khởi động lại pipeline.
  • An toàn: không bao giờ để một ảnh đứng hình trên màn hình vì tài xế sẽ tưởng đó là hình trực tiếp. Khi mất tín hiệu, hiện màn hình đen kèm cảnh báo rõ ràng.
  • Rear camera: one camera. A service listens on CAN (SocketCAN); when it sees the reverse-gear signal it brings the video to the top of the screen with guide lines overlaid. The image must be flipped horizontally.
  • 360° camera: four fisheye cameras (front, rear, left, right). Each image needs lens-distortion correction, projection to a top-down view, then stitching around a picture of the car. This is heavy, so it runs on the GPU (OpenGL), and the four cameras must be time-synchronised.
  • Early start: the rear view must appear very soon after selecting reverse (US rule FMVSS 111 requires it within 2 seconds). So the camera service starts very early in boot and does not wait for the full UI.

Reducing latency

  • No encoding or decoding: use raw formats (YUYV, NV12) and avoid MJPEG/H.264 on the display path.
  • No copying: use DMABUF so the camera, GPU and display share one buffer.
  • Use hardware for colour conversion and scaling instead of CPU videoconvert.
  • Set sync=false on the sink; keep queues small and leaky so they drop old frames rather than pile them up. For a rear camera a fresh image matters more than a complete sequence.
  • Display directly through kmssink or waylandsink.
  • Measure "glass to glass": point the camera at a millisecond clock, photograph the clock and the screen together, and subtract.

Handling dropped frames and faults

  • Detect: every V4L2 buffer has a sequence number; a jump means lost frames. Also watch QoS and ERROR messages on the GStreamer bus.
  • Usual causes: CPU overload, not enough USB bandwidth, too few buffers, poor cable or connector.
  • Recover: use a watchdog; if no new frame arrives within a timeout, restart the pipeline.
  • Safety: never leave a frozen image on screen, because the driver will take it for live video. On signal loss show a black screen with a clear warning.
